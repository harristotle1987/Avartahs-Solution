============================================================ 0. PAYSTACK
COST AND IMPLEMENTATION DECISION
============================================================

Use PAYSTACK as the only payment provider for the first Business OS
release.

Paystack states that integration and maintenance have zero fees. This
does NOT mean payment processing is free. Its published Nigeria pricing
at the time this brief was prepared is: - Local transactions: 1.5% + NGN
100; NGN 100 is waived for transactions under NGN 2,500; local fees are
capped at NGN 2,000 per transaction. - International transactions:
3.9% + NGN 100. - Paystack account activation and live-mode eligibility
are subject to Paystack’s onboarding/approval requirements.

Do not hardcode these fees into customer invoices or claim Avartah
absorbs them. Treat provider fees as Paystack charges and display only
if the product explicitly needs to explain them. Re-check Paystack’s
official pricing before launch because fees can change.

Official documentation: Pricing: https://paystack.com/pricing API:
https://paystack.com/docs/api/ Initialize transaction:
https://paystack.com/docs/api/transaction/#initialize Verify
transaction: https://paystack.com/docs/api/transaction/#verify Webhooks:
https://paystack.com/docs/payments/webhooks/ Verify payments:
https://paystack.com/docs/payments/verify-payments/

IMPORTANT: Do not describe Paystack as completely free. Integration is
free; transaction processing is charged.

============================================================ 3. FILE:
lib/serverAuth.ts — HARDEN SESSION CREATION AND VALIDATION
============================================================

Previous ZIP14 findings: - Secret validation was inconsistent: a cached
secret could pass a 16-character check before the production
32-character requirement. - Session insertion errors were caught/logged
while token creation could continue. - The browser token handling in
lib/auth.ts stores the session token in localStorage.

Required changes: A. Secret handling - Validate SESSION_SECRET once,
before serving requests. - Require at least 32 bytes of
cryptographically random secret material in every production
deployment. - Do not accept short, blank, placeholder or default
secrets. - Do not use weak fallback values. - Fail closed at startup if
the production secret is invalid. - Avoid caching an invalid secret.

B. Session issuance - A session token must never be returned unless the
persistent session record was successfully created in Neon. - If session
insertion fails, return an authentication failure and do not issue a
usable token. - Store only a cryptographic hash of the bearer/session
token in the database where feasible; never store plaintext session
tokens. - Use cryptographically secure random token generation. -
Enforce expiry, revocation and rotation. - Revoke all affected sessions
after credential rotation or suspected compromise. - Validate the user
is active and not suspended on each authenticated request. - Ensure role
changes and account suspension take effect promptly.

C. Token validation - Verify signature using constant-time comparison
where applicable. - Validate issuer, audience, expiry and not-before
claims if using JWT. - Reject malformed, expired, revoked and unknown
sessions. - Never accept identity or role from client-supplied
headers/body as authentication proof. - Resolve user identity and roles
from verified server-side session/database state.

D. Error handling - Return generic authentication errors to clients. -
Do not expose secrets, SQL, stack traces or internal session details. -
Log a safe event ID and security-relevant metadata without tokens or
passwords.

============================================================ 4. FILES:
lib/auth.ts AND context/AuthContext.tsx — SECURE BROWSER AUTH
============================================================

Previous ZIP14 finding: lib/auth.ts stores session tokens in
localStorage. Any successful XSS can read localStorage tokens.

Required architecture: - Prefer server-managed session cookies with
HttpOnly, Secure and an appropriate SameSite policy. - Do not expose
session secrets or privileged credentials to browser JavaScript. -
Remove localStorage token storage after a safe migration to the
cookie-based session mechanism. - Keep one global authentication state
in AuthContext; do not introduce duplicate login pages/modals. - Add a
safe session bootstrap endpoint so the frontend can discover the current
authenticated user without reading a token. - On logout, revoke the
server-side session and clear the cookie. - On password change, account
compromise, role downgrade or admin revocation, revoke affected
sessions. - Ensure frontend state is cleared when the server returns
401.

Cookie settings: - Production: Secure=true, HttpOnly=true, Path=/,
explicit SameSite policy. - Use SameSite=Lax where compatible with the
application. - If cross-site cookies are genuinely required, document
why SameSite=None is necessary and enforce CSRF protection. - Do not set
a broad Domain attribute unless required. - Use separate development and
production cookie settings safely.

CSRF: - Implement a synchronizer-token or robust double-submit CSRF
pattern appropriate to the chosen session architecture. - Protect every
state-changing cookie-authenticated endpoint: POST, PUT, PATCH and
DELETE. - Validate Origin/Referer against an explicit allowlist as an
additional defence, not the only defence. - Do not exempt business,
admin, billing, payment or account mutation routes. - Webhook routes are
authenticated by provider signature and should not use browser CSRF
tokens.

Fail closed if required payment configuration is missing. Do not fall
back to mock success.

A. Create a central payment service Create or update a dedicated
server-side service, for example: - lib/paystack.ts or the existing
payment service location. Do not put Paystack secret handling inside
React components.

Service responsibilities: - Initialize transaction. - Verify
transaction. - Verify webhook signature. - Normalize provider
response. - Validate amount/currency/reference/customer/metadata. -
Handle provider timeouts and safe retries. - Avoid logging sensitive
data. - Use HTTPS only. - Set strict network timeouts. - Do not follow
arbitrary redirects from provider requests. - Never trust
client-supplied amount, plan price, currency, email or tenant metadata
without re-resolving and validating them from the database.

B. Payment initialization endpoint Create or update an authenticated
endpoint such as: POST /api/os/payments/initialize

Server must: 1. Authenticate the user. 2. Verify the user has permission
to pay for that tenant. 3. Load the requested plan from the server-side
subscription_plans table/config. 4. Determine the authoritative price
and currency on the server. 5. Reject unknown, inactive or unavailable
plans. 6. Create a cryptographically unpredictable unique transaction
reference. 7. Create a pending payment/order record in Neon before
redirecting to Paystack. 8. Store tenant_id, user_id, plan_id, expected
amount in kobo, currency, reference, status=pending, timestamps and safe
metadata. 9. Call Paystack Initialize Transaction with server-calculated
amount in the smallest currency unit. For NGN, multiply naira by 100 and
use an integer. 10. Validate Paystack’s response structure and ensure
authorization_url and reference are present. 11. Persist the provider
response fields that are safe and necessary. 12. Return only the hosted
authorization URL and public transaction reference to the browser. 13.
Never activate a subscription at initialization. 14. Do not permit the
client to choose an arbitrary amount or override plan price.

C. Paystack callback/return endpoint Create a callback endpoint that
accepts a transaction reference, but treat it only as a trigger to
verify.

The callback must: - Never trust a browser success query parameter. -
Look up the pending payment by reference in Neon. - Resolve tenant,
plan, amount and currency from the stored record. - Call Paystack’s
server-side Verify Transaction API. - Require provider status=success. -
Compare exact transaction reference. - Compare exact amount in kobo. -
Compare exact currency. - Confirm transaction belongs to the intended
customer/account where available. - Confirm the payment is for the
intended tenant and plan. - Reject mismatches and keep payment
pending/failed as appropriate. - Use an atomic database transaction to
mark payment successful and activate/renew the subscription exactly
once. - Be idempotent if the user refreshes or Paystack redirects
repeatedly. - Never activate paid access solely because the browser
returned to the callback.

D. Verification endpoint Replace the unsafe implementation around
api/businessOSRouter.ts lines 1466–1497.

The endpoint must: - Require authenticated user and appropriate tenant
membership. - Accept only a reference, not a client-supplied price or
authoritative plan. - Find the existing pending transaction. - Verify
through Paystack’s API from the server. - Validate amount, currency,
reference, tenant, customer and success status. - Atomically process
once. - Return current transaction/subscription status without exposing
secret provider payloads. - Reject unknown, reused-for-different-order,
forged, expired or mismatched references.

E. Webhook endpoint Create a dedicated endpoint, for example: POST
/api/os/payments/paystack/webhook

Important implementation requirement: - Paystack webhook signature must
be validated using the exact official mechanism documented for the
account/integration mode. - Read and preserve the raw request body bytes
before JSON parsing. Do not re-serialize parsed JSON to calculate a
signature. - Use Node crypto HMAC SHA-512 and constant-time comparison
according to the current official Paystack documentation. - Support the
currently required Paystack signature header format. Paystack
documentation may use Paystack-Signature with timestamp/key ID
signatures for newer signing-secret mode and x-paystack-signature for
legacy secret-key signing. Implement the currently configured official
mode correctly; do not guess or accept an unsigned event. - For
timestamped signatures, enforce the documented freshness window and
constant-time comparison. - Reject invalid/missing signatures with
401. - Never trust event fields until signature validation succeeds. -
Process only relevant successful charge events for subscription
activation. - Ignore unrelated event types safely. - Persist provider
event IDs or a deterministic idempotency key and enforce a unique
database constraint. - Duplicate/replayed webhook deliveries must not
duplicate payments, invoices or subscriptions. - Verify transaction
details server-to-server where appropriate before granting paid
access. - Check reference, amount, currency, customer, tenant and plan
against the pending database record. - Acknowledge valid events
promptly; use a reliable persisted processing state/outbox if processing
is deferred. - Handle provider retries safely. - Never let a webhook
create a subscription from arbitrary metadata without a pre-existing
pending payment record. - Record failed signature and mismatch attempts
safely without logging secrets or full sensitive payloads.

F. Payment state machine Use explicit states, for example: created ->
pending -> success created -> pending -> failed created -> pending ->
abandoned success -> refunded/reversed only through verified provider
event and reconciliation rules

Never allow: - failed -> success from client input - pending -> active
subscription without verification - a duplicate event to create another
entitlement - a refund/reversal to be silently ignored

Keep payment state and subscription state distinct.

G. Reconciliation Add a safe administrative reconciliation process: -
Find old pending transactions. - Verify status with Paystack
server-side. - Update only from authoritative provider results. -
Rate-limit and audit reconciliation. - Never accept a manual reference
as proof of payment. - Require explicit platform-admin authorization for
any manual correction and record an immutable audit entry.
