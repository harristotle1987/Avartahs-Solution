D. CONTINUOUS DISCOVERY — BOUNDED, NOT INFINITE
Implement automatic continuation across provider pages/batches:
- Process candidates in controlled batches (initially 50 raw candidates where the source supports it).
- Qualify candidates before requesting another batch.
- Stop immediately when 20 genuinely qualified prospects are reached.
- Continue while fewer than 20 are qualified and useful source pages/cursors remain.
- Stop when sources are exhausted, a hard candidate/request/time budget is reached, all providers are unavailable, or the administrator stops the job.
- Initial safety limits: maximum 500 raw candidates per search job; maximum 20 qualified prospects; provider concurrency 2–3; a bounded total job duration compatible with the deployment platform.
- Make limits configurable server-side, not freely controlled by the browser.
- Do not pretend that repeating the same query or re-reading the same first page is pagination. Use provider cursors, offsets or distinct bounded query variations where supported.
- Keep continuation resumable only if the existing deployment architecture can safely support it. Do not rely on an in-memory process surviving a Vercel serverless invocation.
- If background continuation is needed, use the project's existing supported job/cron mechanism. Do not introduce an always-running worker or a new infrastructure dependency without approval.
- Progress/status requests must never start another discovery operation.

E. REDUCE PROVIDER RATE-LIMIT PRESSURE
Audit the existing provider calls in server.ts, including Nominatim, Overpass mirrors, Gemini Google Search/grounding, NVIDIA and LocationIQ.
- Use one primary source first and call a fallback only when needed.
- Do not launch every provider and every query variation in parallel.
- Respect each provider's published usage limits and attribution requirements.
- Nominatim is a particularly sensitive case: do not issue rapid multi-query bursts. Apply a shared per-provider throttle, conservative request spacing, caching and backoff. Do not use it as a high-volume bulk scraping endpoint.
- Do not rotate through Overpass mirrors rapidly as a way to bypass rate limits. Use a small controlled fallback policy, bounded timeouts and cooldowns.
- Avoid the current pattern of trying several Overpass mirrors sequentially on every search when one provider is temporarily slow. Record provider health/cooldown and use fallback only when justified.
- Use AbortSignal timeouts for all outbound requests, including the legacy LocationIQ/Nominatim search route and NVIDIA requests.
- Handle HTTP 429 using Retry-After when present, otherwise bounded exponential backoff with jitter. Do not sleep one second and immediately repeat an exhausted quota request.
- Limit retries; do not retry permanent 4xx errors.
- Avoid duplicate Google/Gemini grounding calls. Do not execute a second grounding search merely because the first result count is below 15 if the provider has already returned no additional evidence or a quota error.
- Cache geocoding and query-expansion results with a reasonable TTL. Reuse cached results for identical normalized category/location searches.
- Keep provider API keys server-side. Never return them to the browser or log them.

F. REMOVE UNNECESSARY NEON WRITES — CRITICAL
The current `/api/prospects/locate` evaluation path writes each qualified prospect to Neon individually and also writes rejected/no-contact candidates to `prospects_excluded`. These writes must be redesigned.
- Keep raw provider results, per-batch deduplication sets, website assessment results and rejected candidates in memory for the active bounded job wherever possible.
- Do not permanently store every raw discovery result.
- Do not insert every candidate with missing contacts into `prospects_excluded`.
- Do not persist every duplicate, provider retry, website crawl, failed lookup or per-candidate progress update.
- Do not store full provider payloads or website HTML.
- Compare normalized candidate keys against Neon in batched lookups, not one SELECT per candidate.
- After qualification, bulk insert qualified candidates in one parameterized batch or a small number of bounded batches inside a transaction.
- Await and handle the database write result. Do not fire-and-forget `pool.query(...).catch(...)` and then return success before persistence is confirmed.
- Use stable identity keys and database uniqueness constraints to prevent repeated search runs from inserting duplicate businesses. A random UUID per discovery is not a deduplication strategy.
- Prefer a canonical key built from normalized domain, normalized phone, and normalized business name plus location, using a safe matching hierarchy. Do not use business name alone where it can collide.
- On conflict, preserve existing authoritative CRM values. Update only missing or demonstrably fresher fields; never overwrite good existing data with null/empty/unverified data.
- Persist only genuinely qualified prospects that pass the contact and website opportunity gates. CRM promotion must remain an explicit administrator action if that is the existing workflow.
- Persist only a compact search-job summary if required: job ID, category/location, timestamps, candidate count, qualified count, duplicate count, excluded counts, provider error counts and terminal status.
- If a temporary staging table is technically unavoidable, justify it, impose a short retention period and clean it automatically. Do not create one by default.
- Do not add unnecessary migrations. Inspect existing prospects schema and indexes before changing them.
