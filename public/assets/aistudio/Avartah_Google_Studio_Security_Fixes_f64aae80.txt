1. P0 — FIX PAYSTACK WEBHOOK PAYMENT ACTIVATION
============================================================

Primary file: api/businessOSRouter.ts
Approximate area in latest audit: webhook handler around lines 1687–1773.
Related files: lib/paystack.ts, payment/subscription migrations and all payment service modules.

CURRENT DEFECT:
The webhook path can use tenant_id and plan_id from webhook metadata to update payment/subscription state without adequately proving that the event corresponds to a pre-existing pending payment with the expected reference, tenant, plan, amount and currency.

REQUIRED IMPLEMENTATION:

A. Treat webhook payload and metadata as untrusted input.
- Verify the webhook signature against the exact raw request body using the currently documented Paystack signing procedure.
- Preserve raw request bytes before JSON parsing. Do not stringify parsed JSON and assume it is equivalent to the original signed bytes.
- Use the correct configured Paystack secret/signing key for the selected environment.
- Compare signatures using a constant-time comparison after validating their encoding and length.
- Reject missing, malformed or invalid signatures with an appropriate non-success response.
- Do not accept unsigned events or a fallback signature scheme invented by the application.
- Check current official Paystack webhook documentation before implementing signature details. Do not assume a timestamped signature format unless Paystack documents and uses it for this integration.

B. Require a pre-existing payment record.
- Find the payment by the exact Paystack reference in the verified event.
- The payment record must already exist in Neon and must be in the pending state.
- Never create a new payment solely from webhook metadata.
- Never trust webhook metadata as the authority for tenant_id, user_id, plan_id, amount, currency or entitlement.
- Load tenant, user, plan and expected amount from the stored pending payment record and trusted database records.
- Reject unknown references, already-invalid references, mismatched tenants, mismatched plans and inconsistent payment records.
- If an event is a duplicate for an already completed payment, handle it idempotently without granting another subscription or extending entitlement again.

C. Verify the transaction with Paystack server-to-server.
- Call Paystack's transaction verification endpoint using the stored reference.
- Require provider status to be successful.
- Require the provider's returned reference to exactly equal the stored/requested reference.
- Compare provider amount in kobo against the expected stored amount in kobo.
- Compare currency exactly against the stored expected currency (NGN for this configured Nigerian payment flow).
- Validate customer identity/email against the expected payment/customer record where available.
- Validate any required channel or transaction identifiers according to the actual Paystack response contract.
- Do not accept a browser callback or webhook metadata as proof of payment.

D. Atomic database transition.
Within one Neon/PostgreSQL transaction:
1. Lock or conditionally claim the pending payment row.
2. Confirm the row remains pending and all expected fields still match.
3. Mark the payment successful and store the verified provider transaction ID/reference and safe verification metadata.
4. Activate or update the subscription from the plan stored in the payment row.
5. Update the tenant entitlement/plan using server-calculated plan data.
6. Record an audit event.
7. Commit all changes together.
If any operation fails, roll back all changes.

Use conditional updates such as UPDATE ... WHERE id = $1 AND status = 'pending' RETURNING ... and verify exactly one row was returned. Use row locking where appropriate. Prevent concurrent duplicate webhook deliveries from applying the same entitlement twice.

E. Event deduplication.
- Add a durable webhook event table or equivalent event-idempotency mechanism if not already present.
- Use a unique constraint for the Paystack event identifier where available. If the provider event does not expose a stable unique ID, use a carefully defined deterministic event identity based on the provider reference and event type, while still retaining the transaction reference as the primary payment idempotency key.
- Claim the event atomically using INSERT ... ON CONFLICT DO NOTHING RETURNING ...
- Only the request that successfully claims a new event may process it.
- Do not use a separate SELECT-then-INSERT race-prone pattern.
- A duplicate event must not create another subscription or reset the subscription period.

F. Event types.
- Process only documented Paystack event types relevant to successful transactions.
- A charge.success event is not sufficient by itself; perform all database and provider verification above.
- Do not let failed, abandoned, reversed, refunded or unrelated events activate a plan.
- Implement appropriate state transitions for refunds/reversals only if the current product requirements support them. Otherwise record them for reconciliation and alerting without granting new entitlements.
- Never downgrade or cancel a subscription from an unverified event.

G. Webhook response and resilience.
- Return success only after the event has been durably recorded and processed or safely queued.
- For temporary database/provider errors, return a retryable non-2xx response so Paystack can retry.
- Do not log secrets, full card data, authorization headers, session tokens or unnecessary personal/payment data.
- Add structured safe logs with event type, internal payment ID, reference suffix or safe correlation ID, processing result and timestamp.
